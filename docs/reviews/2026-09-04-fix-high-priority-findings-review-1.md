## Assessment
The plan correctly decomposes all seven high-priority findings into ordered, test-backed phases that preserve the Textual/pure-function architecture. Current State claims verify line-for-line and the baseline reproduces (247 passed, ruff clean, pyrefly 0 errors / 84 suppressed / 10 hidden). It is not implementable as written: the coordinator's cross-thread release is racy, several automated gates match the wrong strings, and key signatures/ownership rules are underspecified.

## Cross-Cutting Themes
- **Thread-ownership vs worker release.** Phases 1–2 add UI-thread-owned state (`ServerIdentity`, `OperationCoordinator`) but release it from worker `finally` callbacks without a lock or `call_from_thread` rule. The same pattern repeats for chat, swap, and delete.
- **Gates that pass vacuously.** Three `rg` success criteria either already pass pre-fix (`find_server_pid\(\)`), always match (`replace\(`, `auto|warm|restart`), or contradict keeping a symbol for diagnostics (`model_from_cmdline`).
- **Underspecified boundaries.** Loopback set, `net_connections` permission failure, stop-command timeout value, policy priority when rules overlap, `max_tokens` source for preview vs send, and `TurnResult` field migration are all load-bearing details left to the implementer.

## Findings

### Critical
- **[Correctness]** Phase 2 (`src/mlx_tui/app/operations.py`, `src/mlx_tui/chat_pane/turn.py:161-163`, `src/mlx_tui/models_pane/swap_ops.py:86-161`): `OperationCoordinator` is specified as "UI-thread-owned" with `try_acquire`/`release` and owner-only release, but `CHATTING` is released "from the worker's unconditional `finally` callback", and swap/delete releases also run in `@work(thread=True)` workers. Direct mutation from worker threads races with UI-thread acquire; check-then-clear on `current` is TOCTOU and a late worker can still interleave with a newer lease. Fix: either guard `current` with a `threading.Lock` and document that acquire/release are thread-safe, or mandate that workers only release via `call_from_thread(coordinator.release, kind)` and the owner check runs on the UI thread. Add a unit test with two threads racing acquire/release.
- **[Correctness]** Phase 2 input ownership (`src/mlx_tui/app/swap_ctrl.py:19-30`, `src/mlx_tui/chat_pane/turn.py:232-237`): two owners drive `#chat-input.disabled` — `set_operation_ui(busy)` disables/restores table+input+progress on swap/delete, while `end_turn()` re-enables input `if not swap_busy`. After the refactor `swap_busy` reads `operations.is_swap_busy`, but a warm swap finishing under a live turn, a delete finishing under chat, and chat finishing under a queued swap all have different correct outcomes. As written the input can be prematurely re-enabled mid-turn or stranded disabled. Fix: define one rule (e.g. `end_turn` re-enables only when `coordinator.current in (IDLE, CHATTING)` and yields to `set_operation_ui`; or make the coordinator the sole writer of `disabled`).

Fix: gate on absence — `rg -n "AppConfig\(|_system_prompt" src/mlx_tui/app/presets_ctrl.py src/mlx_tui/chat_pane src/mlx_tui/app/config_edit.py` should return only the `system_prompt` property definition and no `AppConfig(` construction.
- **[Plan Mechanics]** Phase 3 gate (`rg -n "swap_policy|auto|warm|restart" README.md src/...`): bare `auto|warm|restart` matches `automatic`, `warning`, etc. Fix: `rg -n "swap_policy" README.md src/mlx_tui/config.py src/mlx_tui/models_pane/swap_ops.py` plus `rg -n '"auto"|"warm"|"restart"'` for the literal policy strings.
- **[Correctness]** Phase 1 listener discovery (`src/mlx_tui/process.py:35-51` → `find_server_process(host, port, pidfile)`): `psutil.net_connections(kind="tcp")` on macOS requires root (verified in `psutil` help: "On macOS this function requires root privileges"; returns `pid=None`/`-1` or raises `AccessDenied` otherwise). The target platform per `README.md:19-24` is macOS Apple Silicon, so the primary PID path will ~always yield `None` without a pidfile, leaving RSS unavailable and degrading the memory story the plan claims to fix. The plan also never defines the loopback set (`127.0.0.1`? `::1`? `localhost`? `0.0.0.0`?), nor `AccessDenied` handling, nor negative-permission caching (exception every 2s poll). Fix: define `LOOPBACK_HOSTS`, catch `(psutil.AccessDenied, PermissionError, RuntimeError)` → `None`, cache the permission-denied outcome to avoid a syscall storm, and document that pidfile is the supported macOS telemetry path.
- **[Correctness]** Phase 2 bounded stop/start (`src/mlx_tui/serverctl.py:41-45`, `src/mlx_tui/models_pane/swap_ops.py:86-161`): "add bounded command execution for `stop_cmd` … and terminate a spawned start process on failed startup/health timeout" has no timeout value, no signature (`run_command(..., timeout_s: float | None)`?), no kill-vs-terminate policy, and no handle ownership (who keeps `proc` to terminate it on `wait_healthy` timeout while preserving the successful long-running server). Without this F9 is not fixed — a hung `stop_cmd` still holds `RESTARTING` forever. Fix: specify e.g. `run_command(cmd, on_line, timeout_s=30.0)` raising `TimeoutExpired`, and `run_boot_impl` `try/finally` that `proc.terminate()` (then `kill()` after grace) only on failure arms, plus a hung-stop test.
- **[Correctness]** Phase 3 policy priority (`src/mlx_tui/models_pane/swap_ops.py:17-44`, `src/mlx_tui/config.py:12-26`): `auto` rules overlap — "restarts when both commands are configured" vs "cold-start path when the endpoint is down with a start command" vs "warm load when green and restart unavailable". With both commands configured and endpoint red/amber, is it restart or cold-start or refuse? With amber (proxy squatting) and commands, restart or refuse? Fix: add an explicit decision table (e.g. amber → refuse regardless; both cmds → restart regardless of green/red; green + no cmds → warm; red + start_cmd only → cold-start; else refuse with message).
- **[API/Compatibility]** Phase 3 `wait_healthy`/`warm_load` migration: new `wait_healthy() -> ServerProbe | None` "removes the `current_model` callback" but says nothing about existing `is_running`/`on_tick`/`timeout_s` params (`src/mlx_tui/serverctl.py:93-123`, used at `src/mlx_tui/models_pane/swap_ops.py:131-138`). Dropping `is_running` regresses instant-crash detection (waits the full deadline after the child dies). New `WarmLoadResult(response_model)` vs "return an optional string `model`" is inconsistent (dataclass vs bare `str | None`). Fix: pin the new signatures verbatim (`warm_load(...) -> WarmLoadResult`; `wait_healthy(url, *, target_model, is_running, timeout_s, on_tick) -> ServerProbe | None`) and update the one callsite + `tests/unit/test_serverctl.py:120-290` accordingly.
- **[Architecture & Patterns]** Phase 6 `system_prompt` property (`src/mlx_tui/chat_pane/__init__.py:28,159-160`, `src/mlx_tui/chat_pane/params.py:72-76`): making it "backed by `self.tui.config.system`" couples the pane to a live `App` (`self.app`) for a plain data access. Existing `apply_config_params(pane, cfg)` is app-free and unit-testable; the new property breaks headless `test_params.py` usage. `set_system_prompt()` updating `app.config` via `replace()` also leaves a stale writer (presets path already uses `replace` directly). Fix: keep a plain `_system_prompt` cache synced totally from `cfg` in `apply_config_params` (including clearing on `None`), and make `turn.py` read the passed-in `cfg.system` rather than reaching into `app.config` through the pane.
- **[Test Coverage]** Phase 7 revision plumbing (`src/mlx_tui/search.py:54-56`, `src/mlx_tui/search_screen/query.py:97-104`, `src/mlx_tui/search_screen/download.py:55-62`): `repo_snapshot(api, repo_id) -> RepoSnapshot` reads `ModelInfo.sha` (verified to exist, and `snapshot_download(revision=...)` exists), but the `HubApi` protocol (`src/mlx_tui/search.py:24-29`) and `_StubApi` in `tests/unit/test_search.py:31-51` return `SimpleNamespace(siblings=...)` with no `sha` — every updated test will `AttributeError`. `sha=None` handling is unspecified. `_revisions` "clear with stale result state" never says when (on `populate`? on new search? on size failure?). Fix: extend the protocol to `model_info(...) -> ModelInfo` with `sha: str | None`, update fakes, define `sha is None → revision=None` passthrough, and clear `_revisions` in `populate()` (and on empty-submit clear in `query.py:24-39`).
- **[Test Coverage]** Phase 4 `max_tokens` source (`src/mlx_tui/chat_pane/__init__.py:93-109`, `src/mlx_tui/chat_pane/turn.py:36-81`): pre-submit preview and send path must use the same `max_tokens` (parsed widget vs `tui.config.max_tokens`). A user editing `#param-max-tokens` without submitting changes the send reservation but not the preview bar (or vice versa). Fix: name the source once (e.g. preview calls `params.parse_params` too, or both take `max_tokens` from the `ContextWindow` input) and assert payload `estimate + max_tokens <= max_ctx` in the integration test that "captures the outgoing payload".
- **[Performance]** Phase 1 poll cost (`src/mlx_tui/app/polling.py:35-65` every 2.0s): system-wide `net_connections` + per-process `cmdline()`/`create_time()` on every tick is the most expensive call in the poll loop. On permission-denied macOS it is pure overhead. Fix: only scan when endpoint is loopback, short-circuit on cached `(pid, create_time)` hit before scanning connections, and skip the scan entirely once permission-denied is cached (until pidfile appears).
- **[Performance]** Phase 3 double wait: warm path becomes `warm_load(timeout=health_timeout)` then `wait_healthy(timeout=health_timeout)` sequentially — worst-case 2× the current block while holding `LOADING`. Fix: state the intended budgets (e.g. short probe timeout + full health wait) or reuse one deadline.

### Suggestions
- **[Performance]** Cache the `net_connections` permission-denied outcome and the `(pid, create_time)` hit; log at most once.
- **[Correctness]** Have `prepare_context()` return a rejected-reason string alongside `ContextLimitError` so the log line is actionable ("newest message ~X tok + reserved Y tok > max_ctx Z").
- **[Architecture & Patterns]** Rename the two "ctx" meanings while touching both: context bar shows the *request reservation* (`input + max_tokens`), Metrics `ctx` stays *prompt depth*. A `req`/`ctx` label split avoids the next confusion.
- **[Security]** Mirroring `*.py` into `ALLOW_PATTERNS` matches the loader but pulls executable code. Note it in the README alongside the pattern list (report F7 already asks for an explicit custom-code limitation).

2. Repair the four vacuous gates (Major 1–4): `find_server_pid\(`, explicit shim deletion, absence-only preset gate, word-boundaried policy gate.

5. Pin overlapping contracts (Major 7–8, Minor 5–7): policy decision table; verbatim `warm_load`/`wait_healthy`/`stream_turn` signatures with `is_running`/`on_tick` preserved; deleted `TurnResult` string fields; `TurnRecord` field-count updates.
